AynzamAI · Wie das Web funktioniert

Von der URL bis zum Pixel

Was wirklich passiert, wenn du aynzam.ai eintippst und Enter drückst — Schicht für Schicht: URL, DNS, IP, TCP, TLS, HTTP, und am Ende die fertige Seite. Alles von Grund auf, visuell, mit Animationen.

Die ganze Kette in einem Satz

Die URL sagt wohin → DNS übersetzt den Namen in eine IP → TCP baut die Verbindung auf → TLS verschlüsselt sie → über HTTP fragt der Browser die Seite an und bekommt sie zurück → der Browser rendert daraus Pixel.

Teil A · Adresse & Namen

01Anatomie einer URL

Eine URL (Uniform Resource Locator) ist die vollständige Adresse einer Ressource im Web. Sie hat feste Bestandteile — jeder beantwortet eine eigene Frage.

Abb. 1 — Die Bestandteile einer URL
  • Schema (https): welches Protokoll gesprochen wird — hier verschlüsseltes HTTP.
  • Host (aynzam.ai): der Domainname des Servers, den du erreichen willst.
  • Port (:443): die „Tür" am Server. 443 für HTTPS, 80 für HTTP — meist unsichtbar, weil Standard.
  • Pfad (/pricing): welche konkrete Seite/Ressource.
  • Query (?ref=mail): zusätzliche Parameter als Schlüssel-Wert-Paare.
  • Fragment (#faq): Sprung zu einem Abschnitt innerhalb der Seite — wird nie an den Server geschickt.

02Anatomie einer Domain

Der Host-Teil ist die Domain. Man liest sie von rechts nach links, von „groß" nach „klein". Jeder Punkt trennt eine Ebene.

Abb. 2 — Ebenen einer Domain

Apex-Domain ist die nackte Form aynzam.ai. www ist nur eine Subdomain — wie blog.aynzam.ai. Beide sind für das Internet zwei verschiedene Adressen, jede mit eigenem DNS-Eintrag und SSL-Zertifikat.

03IP-Adressen — die echten Hausnummern

Namen sind für Menschen. Computer finden sich über IP-Adressen. Jeder Server im Netz hat eine — sie ist die eigentliche Hausnummer, hinter der die Domain nur ein gemerktes Etikett ist.

Abb. 3 — Name ↔ IP
  • IPv4 (104.21.16.71): vier Zahlen 0–255, also 32 Bit. Reichte für ~4 Mrd. Adressen — heute zu wenig.
  • IPv6 (2606:4700:…): 128 Bit, praktisch unbegrenzt viele Adressen. Löst die Knappheit.
  • Öffentlich vs. privat: Adressen wie 192.168.x.x sind privat (dein Heimnetz), nur öffentliche IPs sind im Internet direkt erreichbar.

04DNS — das Adressbuch

DNS (Domain Name System) ist die weltweite Telefonauskunft: Du fragst nach einem Namen, bekommst die IP zurück. Erst danach kann der Browser die Seite überhaupt abrufen.

Abb. 4 — DNS-Auflösung und Auslieferung
DNS-Anfrage Seitenabruf Cloudflare ↔ Pages

DNS ist hierarchisch und stark zwischengespeichert (gecacht), deshalb dauert die Auflösung meist nur Millisekunden. Erst nach der IP beginnt die eigentliche Verbindung.

Teil B · Die Verbindung

05Das Schichtenmodell (TCP/IP)

Damit so viele Bausteine zusammenspielen, ist das Netz in Schichten gegliedert. Jede Schicht hat eine Aufgabe und verlässt sich auf die darunter. Deine Daten werden beim Senden von oben nach unten „eingepackt" und beim Empfänger wieder ausgepackt.

Abb. 5 — Schichten und Verpackung der Daten

Jede Schicht legt beim Senden ihren eigenen „Umschlag" um die Daten (Header). Beim Empfänger wird Schicht für Schicht wieder ausgepackt. So muss HTTP nichts über WLAN wissen — es verlässt sich einfach auf TCP, TCP auf IP, und so weiter.

06TCP — der Verbindungsaufbau

Bevor Daten fließen, einigen sich Browser und Server per 3-Wege-Handshake auf eine Verbindung. TCP sorgt danach dafür, dass alle Pakete vollständig und in richtiger Reihenfolge ankommen.

Abb. 6 — TCP 3-Wege-Handshake (SYN · SYN-ACK · ACK)
TCP gegen UDP

TCP ist der zuverlässige Bote: er bestätigt jedes Paket und sortiert sie — ideal für Webseiten. UDP ist der schnelle, ungesicherte Bote ohne Handshake — ideal für Video-Calls oder Spiele, wo Tempo wichtiger ist als jedes einzelne Paket. (HTTP/3 nutzt UDP, dazu gleich.)

07TLS — die Verschlüsselung (das „S" in HTTPS)

Nach dem TCP-Handshake folgt der TLS-Handshake. Er macht aus HTTP das sichere HTTPS: Er prüft per Zertifikat, dass du wirklich mit aynzam.ai sprichst, und handelt einen geheimen Schlüssel aus, mit dem ab dann alles verschlüsselt wird.

Abb. 7 — TLS-Handshake: Identität prüfen, Schlüssel aushandeln

Der Clou: Zum Aushandeln wird asymmetrische Kryptografie genutzt (öffentlicher/privater Schlüssel im Zertifikat), danach ein schneller symmetrischer Sitzungsschlüssel. Das Zertifikat stellt eine Zertifizierungsstelle aus — bei dir automatisch über Cloudflare, deshalb war es so wichtig, dass www.aynzam.ai als Domain hinzugefügt wurde (sonst kein Zertifikat, kein HTTPS).

Teil C · Das Gespräch (HTTP)

08HTTP — Anfrage und Antwort

Steht die verschlüsselte Verbindung, redet der Browser mit dem Server über HTTP (HyperText Transfer Protocol). Das Muster ist immer gleich: der Browser schickt eine Anfrage, der Server schickt eine Antwort.

Anfrage (Browser → Server)
GET /pricing HTTP/2
Host: aynzam.ai
Accept: text/html
User-Agent: Chrome/…
# „gib mir die Preis-Seite"
Antwort (Server → Browser)
HTTP/2 200 OK
Content-Type: text/html
Content-Length: 64989
Cache-Control: max-age=14400

# … der HTML-Inhalt …

Die wichtigsten HTTP-Methoden (Verben)

MethodeBedeutungBeispiel
GETEtwas holen (lesen, verändert nichts)Seite, Bild, Daten abrufen
POSTEtwas neu anlegen / absendenFormular, Login, Demo-Buchung
PUT / PATCHEtwas ändern (ganz / teilweise)Profil aktualisieren
DELETEEtwas löschenEintrag entfernen

Header sind Zusatzinfos zu jeder Anfrage/Antwort (Inhaltstyp, Cache-Regeln, Cookies, Sprache …). Der eigentliche Inhalt (HTML, JSON, Bild) heißt Body.

09HTTP-Statuscodes

Jede Antwort beginnt mit einem dreistelligen Code. Die erste Ziffer verrät die Kategorie — den 404 von vorhin erkennst du jetzt sofort.

2xx — Erfolg
Hat geklappt. 200 OK, 201 Created
3xx — Weiterleitung
Woanders suchen. 301 (dauerhaft, wie www→apex), 302
4xx — Dein Fehler
Anfrage stimmt nicht. 404 nicht gefunden, 403 verboten, 401
5xx — Server-Fehler
Server hat ein Problem. 500, 502, 503

Der DEPLOYMENT_NOT_FOUND-Fehler war ein 404: die Adresse zeigte auf ein Deployment, das es nicht mehr gab.

10HTTP-Versionen: 1.1, 2, 3

HTTP hat sich weiterentwickelt — vor allem, um schneller mehrere Dinge gleichzeitig zu laden.

Abb. 8 — Entwicklung von HTTP
  • HTTP/1.1: eine Anfrage nach der anderen pro Verbindung — bei vielen Dateien entsteht ein Stau.
  • HTTP/2: viele Anfragen gleichzeitig über eine einzige TCP-Verbindung (Multiplexing). Deutlich schneller.
  • HTTP/3: läuft über QUIC (auf UDP statt TCP) — schnellerer Verbindungsaufbau und kein Blockieren, wenn ein Paket fehlt. Deine Seite spricht bereits HTTP/2.
Teil D · Alles zusammen

11Die komplette Reise: aynzam.ai eintippen

Jetzt alle Bausteine in einer Kette — von Enter bis zum fertigen Bild. Das alles passiert typischerweise in unter einer Sekunde.

Abb. 9 — Die komplette Reise einer Anfrage
  1. URL — du tippst aynzam.ai und drückst Enter.
  2. DNS — der Name wird zur IP von Cloudflare aufgelöst.
  3. TCP — 3-Wege-Handshake baut die Verbindung auf.
  4. TLS — Zertifikat prüfen, Schlüssel aushandeln, ab jetzt verschlüsselt.
  5. HTTP — der Browser schickt GET /.
  6. Antwort — Cloudflare liefert HTML, CSS, Bilder aus dem Pages-Projekt.
  7. Render — der Browser baut daraus die sichtbare Seite (Pixel).
Teil E · Deine Domain konkret

12www gegen Apex — zwei Türen, ein Raum

Dieselbe Seite ist unter zwei Adressen erreichbar. Beide führen ins gleiche Pages-Projekt — eine ist der „offizielle" Eingang, die andere leitet dorthin weiter.

Abb. 10 — www leitet per 301 auf den Apex

13Warum überhaupt weiterleiten?

Läuft dieselbe Seite unter zwei Adressen, willst du eine zur kanonischen machen:

  • SEO: sonst sieht Google zwei Seiten mit gleichem Inhalt → das Ranking verteilt sich statt sich zu bündeln.
  • Konsistenz: Cookies, Cache, Links und Analytics zersplittern sonst auf zwei Hosts.

Bei dir ist aynzam.ai das Ziel, www leitet per 301 dorthin. Welche „Haupt" ist, ist Geschmackssache — wichtig ist nur, dass es eine gibt.

14Die echten DNS-Einträge

AdresseTypZeigt aufStatus
aynzam.aiA / CNAME-FlatteningCloudflare Pages (intern aufgelöst)aktiv
www.aynzam.aiCNAMEai-website-bis.pages.devaktiv (neu)
www (vorher)A192.0.2.1 — Platzhalter, leertot
Technik-Detail

Eine Subdomain wie www darf per CNAME auf einen anderen Namen zeigen. Der Apex darf das klassisch nicht — Cloudflare löst das mit „CNAME-Flattening" intern. Der alte www zeigte auf 192.0.2.1, eine reservierte Platzhalter-IP ohne Server dahinter — daher kam keine Antwort.

15Warum du noch das alte Design sahst

Der Server lieferte längst das neue Design — dein Browser zeigte das alte, weil er style.css und das Favicon aus dem Cache nahm.

Abb. 11 — Cache-Treffer (oben) gegen frischen Abruf (unten)

So leerst du den Cache

  • Hard-Refresh: Cmd + Shift + R auf der Seite.
  • Favicon hartnäckig: einmal aynzam.ai/favicon.svg direkt aufrufen, Tab schließen, neu öffnen.
  • Ganz sicher: Chrome → Einstellungen → „Browserdaten löschen" → nur „Bilder und Dateien im Cache".

So kommt eine Änderung von deinem Rechner auf aynzam.ai. Jeder Push auf main löst bei Cloudflare Pages einen Build aus.

Abb. 12 — Push → Build → Deploy → Live
